# Research — 081, closing the audit's product gaps

Phase 0. Five parallel read-only investigations (self-call guard; service endpoints and the index; truthful claims; releases and iOS privacy; hygiene and the service repos). Everything below is measured in the tree at `746e2259`, with file:line so the implementation does not have to re-derive it.

## 1. Self-call guard (spec items 5, FR-005/FR-006)

**Decision**: a new pure kernel `rust/crates/vela-core/src/app/self_call_guard.rs`, hooked into `sign_request.rs` twice — at `on_request_arrived` (before the request becomes pending, ~:1289) and again at `proceed_submit` (~:1605, beside `enforce_no_unlimited`) so a shell-supplied `params_override_json` cannot smuggle a call past the first check.

**Rationale**: `sign_request.rs` is the single entry for every dApp method (`is_signing_method` :550); the shells only normalise `{to, value, data}` and can never choose the Safe `operation` (web `dapp-submit.ts:600`, desktop `executor/sign_request.rs:341`, Android `SignExecutor.kt:269`, iOS `SignExecutor.swift:385`). The unlimited-approval guard (`app/approval_guard.rs`, verdict `enforce_no_unlimited` :2037) is the precedent: a UI gate (`confirm_allowed` :584 → `SignView.confirm_gate_open` :933) plus a fail-closed refusal (`SignErrorKind::UnlimitedApproval` :197, JSON-RPC `-32603`).

**Findings that shape the design**:

- **No self-call detection exists today**; the only same-address heuristic is `to_own_token` (`clear_signing.rs:604`), which is about token burns.
- **Selectors to block** (Safe v1.4.1): `0x0d582f13` addOwnerWithThreshold · `0xf8dc5dd9` removeOwner · `0xe318b52b` swapOwner · `0x694e80c3` changeThreshold · `0x610b5925` enableModule · `0xe009cfde` disableModule · `0xe19a9dd9` setGuard · `0xf08a0323` setFallbackHandler · `0xe068df37` setModuleGuard (v1.5, future-proof) · `0xb63e800d` setup · `0x6a761202` execTransaction · `0x468721a7` / `0x5229073f` execTransactionFromModule[ReturnData]. Recurse through `0x8d80ff0a multiSend(bytes)` (depth cap 4) and through `execTransaction`'s inner `(to, data, operation)`; block any inner `operation == 1`.
- **Typed data is already wrapped**: a dApp's EIP-712 is hashed and re-wrapped as `SafeMessage(bytes)` under the user's own Safe domain (`user_op.rs:382-395`), so a `SafeTx` for *the user's own* Safe is not directly exploitable (`checkSignatures` would need the raw SafeTxHash). The residual case is real though: if the user's Safe is an owner of **another** Safe, a signed `SafeTx` for that parent is a valid EIP-1271 authorisation. Block `primaryType == "SafeTx"` anyway (spec AS-4).
- **Must not break**: the in-band fee leg and the estimation placeholder legitimately target the Safe itself with empty/transfer data (web `safe-transaction.ts:1982`, desktop `executor/user_op.rs:424`). The guard runs on dApp-originated params only, and allows empty-data self-calls.
- **Web has no error surface**: `lib/signing/live.ts` never renders `SignView.error` (desktop `signing/live.rs:570`, Android `SigningLive.kt:277`, iOS `SigningLive.swift:217` all do). Without adding one, a blocked request on web looks silently unsignable. This is part of the work, not a footnote.
- **Wire enums are strict**: adding a `SignErrorKind` variant requires shipping core + generated TS + `SignWire.kt:61` + `SignWire.swift:55` together, or iOS/Android fail to decode the whole view.

**Alternatives considered**: blocking in each shell (rejected — four copies of a money rule, against the core/shell split); warning instead of blocking (rejected — the founder's ruling and the spec's assumption: one signature is irreversible); blocking at UserOp assembly (rejected — too late for typed data, and the fee leg legitimately self-calls).

## 2. Service endpoints and the public-key index (items 1, 2, 6, 4 → FR-001/2/4/7)

**iOS Settings → Service Endpoints** has two independent defects:

1. **Event payload mismatch** — the core expects `{"type":"endpoint_edited","field":…,"value":…}` (`network_admin.rs:1064`), iOS sends `id` (`SettingsStore.swift:219,223`) with fixture ids (`chain-data|passkey|relay|fiat`). Serde rejects it, so the event never reaches `update`. The same class of bug affects `provider_key_edited/blurred`, `provider_test_requested` (`:231-242`), `add_by_chain_id_requested` (`:207`) and `override_field_edited` (`:246`).
2. **No live projection** — `SettingsLive.swift` has no `withEndpoints`, so the page renders fixtures (including the dead host `p256-index-rs.getvela.app` and fake latency badges). The wire types already exist and decode (`SettingsWire.swift:219-231`).

Working references to copy: Android `SettingsLive.kt:335` + `VelaNavHost.kt:1982` + `SettingsController.kt:276`; web `lib/settings/live.ts:388`; desktop `wallet/page.rs:7420`. Save/persist/reset already work core-side once the event decodes (`network_admin.rs:2503` → `NetworkAdminExecutor.swift:128` → `AccountStore.swift:140`). Also `SettingsStore.swift:73` builds `NetworkAdminExecutor` without the RPC pool, so `invalidate_pools` is a no-op after an endpoint change.

**Index ignored** — one cause per shell:

- **web**: `lib/onboarding/core/registry.ts:62` keeps a module-global `baseUrl`; `setRegistryUrl` has **zero call sites**. Fix: read `getPasskeyIndexURL()` per call, the pattern already used by `lib/services/core-walk.ts:49`.
- **desktop**: global mutex `executor/registry.rs:83`, set only from `OnboardingPage::new` (`onboarding.rs:197`); `main.rs:111` builds `WalletPage::signed_in` without it. Also `executor/network_admin.rs:512` saves without calling `set_registry_url`, so a Settings edit needs a relaunch.
- **Android**: `VelaWalletApplication.kt:150` constructs `RegistryClient()` with the default and never assigns `baseUrl`; onboarding is correct (`OnboardingViewModel.kt:216`).
- **iOS**: `OnboardingModel.swift:196` snapshots the URL in `init` for a process-lifetime model; name lookup is already per-call (`RecipientIdentity.swift:150`).

**Decision**: add an `effective_passkey_index_url` accessor to the core beside `effective_ethereum_data_url` (`network_admin.rs:2406`) and have every shell read per call (or re-apply at flow start), so the empty→default rule lives in one place.

**X-Rpc-Url (FR-007)**: senders are web `rpc-pool-executor.ts:190`, `bundler-service.ts:416,483`; desktop `executor/pool.rs:674`, `executor/relay.rs:99`; Android `RpcPoolExecutor.kt:287`, `RelayClient.kt:535`; iOS `RelayClient.swift:63`. The relay reads **only** `x-vela-rpc-url` (`vela-relay/src/utils/rpc.rs:14`, `vela-relay-cf/src/arms/rpc.rs:12`) — there is no `x-rpc-url` anywhere in the relay. **Removal is functionally inert** (CORS is permissive on both, so no preflight changes). Keep the core's `best_rpc_url` verdict: the web simulator seeds a tevm fork from it (`sim-engine-tevm.ts:80`).

**Self-hosting guide link (FR-004)**: copy key `settingsModals.endpoints.selfHostGuide` (15 locales). Web links the repo root (`EndpointsPanel.svelte:41`); desktop renders a plain `div` with no click handler (`wallet/page.rs:7517`) while the app's idiom is `cx.open_url` (`wallet/page.rs:4926`). Phones have no such row — adding one is a design choice, not a bug (`fixtures.test.ts:275` asserts its absence).

## 3. Truthful claims (items 7, 8, 14 → FR-008/9/10/11)

**Descriptor provenance (FR-008)**: the ladder and the `verified` flag live entirely in `app/clear_signing.rs` (built-in `local_descriptor()` :4259 → fetched contract descriptor :1643 → token-standard shapes :1659 → fetched ERC fallbacks :1746 → 4-byte DB `best_effort_result()` :2335 → blind :1139). `verified` is set from `is_specific` (:2209, :2298) and **built-in and fetched are indistinguishable on the wire** (`ClearSignResult` carries no provenance). No executor authenticates anything (web `clear-executor.ts:80`, desktop `executor/clear_signing.rs:49`, Android `ClearExecutor.kt:28`, iOS `ClearExecutor.swift:49`), and the base URL is user-editable.

**Decision**: add `provenance: ClearProvenance { BuiltIn, PinnedMatch, Fetched, Standard, SelectorDb }` to `ClearSignResult`; `verified` becomes `BuiltIn | PinnedMatch`, where `PinnedMatch` means a fetched descriptor that equals the built-in one for that address (serde_json `Value` equality is order-independent without `preserve_order`).

**Consequence to handle**: every EIP-712 "verified" today comes from a *fetched* descriptor (`clear_signing.rs:1833`), so this downgrades permit-style sheets unless typed descriptors are also built in. Plan: bundle the typed descriptors Vela already relies on (ERC-2612 permit, Permit2) as built-ins, then measure what remains.

**Also found (fix while here)**: desktop labels `partial` with `verifiedAbiWarning` (`signing/live.rs:848`) and web maps `!verified` to `selectorNotListed` (`live.ts:268`) even for ordinary token-shape decodes — both are wrong strings for the state.

**Network admission (FR-009)**: `network_admin.rs:97-133` requires 11 contracts; `SafeWebAuthnSignerFactory 0x1d31F259…1195` and its singleton `0x4E27b513…5CA50` (`safe.rs:36-37`) are **absent**, though `encode_setup_data` (`safe.rs:220`) calls the factory once per extra key — a multi-key Safe on a chain without it is **undeployable**. `CompatibilityFallbackHandler` (`safe.rs:25`) **is** required but unused: wallets set the 4337 module as fallback handler (`safe.rs:259`); the site already documents this (`security-audits.md:209`). The site mirrors the list in `chain-setup/required-contracts.ts:44-130` with a drift test that reads the Rust file (`required-contracts.test.ts:20`), and `deployment-data.json` would need CREATE2 payloads for the two new entries. Readiness reaches users through `NetCompatibility{compatible, contracts[], p256_available, rpc_failure}` (:766) — iOS shows no P-256 row at all (`SettingsLive.swift:529`, a documented gap).

**Decision**: required set becomes the 12 the wallet actually uses (drop the fallback handler, add the factory + singleton), and `NetCompatibility` gains `multi_key_ready` so single-key readiness can be reported separately; ≈3 new corpus keys × 15 locales plus site strings.

**Forward-verified names (FR-010)**: four duplicated shell implementations (web `recipient-identity.ts:50`, desktop `executor/identity.rs:52`, iOS `RecipientIdentity.swift:56`, Android `IdentityResolver.kt:126`), five services (.bnb, .arb, .g, Basename via ENSIP-19 `node(address)`, ENS), **no forward verification anywhere**; only positive results are cached for 24 h. The core already owns an equivalent transcript machine for the registry walk (`registry_lookup.rs:413`, exported as `registryNameStep` and driven by all four shells), which is the pattern to copy: the core owns namehash, the forward step (`resolver(namehash)` → `addr(bytes32) 0x3b3b57de`, ENSIP-10 `resolve(bytes,bytes) 0x9061b923` for wildcard/CCIP names like many Basenames), the case-insensitive address comparison and the rule that only verified positives are cached; the shells keep the `eth_call` transport.

**Network count (FR-011)**: corpus `rust/crates/vela-core/i18n/locales/<lng>/onboarding.json` keys `welcome.featureOneAddressTitle` (:10), `intro.chainsBody` (:33), `welcomeWeb.meta.description` (:38), `welcomeWeb.features.oneAddress.title` (:48) — ≈60 strings over 15 locales; plus non-corpus copy in `extension/manifest.json:5`, `packaging/app.getvela.VelaWallet.metainfo.xml:41`, `packaging/vela-wallet.spec:65`, `packaging/deb/control.in:22`. The site and store copy already say 24. Corpus edits follow the documented gate (`docs/localization.md:237`, `rust/README.md:137`): `gen:i18n` → `lint:i18n` → `verify:i18n` → `dump:vectors` → `build:wasm` + `sync:wasm` → `cargo test -p vela-core --features crux,i18n-all`. Skipping `dump:vectors` leaves `tests/vectors/i18n-exhaustive.json` stale and CI fails with a misleading message.

## 4. Releases and iOS privacy (items 9, 10 → FR-012/13/14)

**Provenance (FR-012)**: `release.yml:141-243` (`publish`) is the one place every artifact exists together (`packages/`), so attestation goes there: add `id-token: write` + `attestations: write` to the job's permissions (`:147`) and one `actions/attest-build-provenance@v2` step between the checksum step (:192) and the notes step (:201). Per-packaging-workflow attestation is rejected: reusable workflows cannot exceed the caller's permissions, and they also run on PRs. Verification becomes `gh attestation verify <file> --repo mondaylabsltd/vela-wallet` (public repo → free), optionally pinned with `--signer-workflow …/release.yml`. The same two permissions and step go in `clearsigning-package.yml:97`.

**macOS is the exception**: the CI signing path exists but the `release` environment is empty, so `publishable=false` and the `.dmg`s are built, signed, notarized and attached **by hand** (`app-desktop/vela-wallet/scripts/release-macos-local.sh`, `scripts/release-attach.sh`). Workflow provenance cannot honestly cover them. Decision: document notarization as the macOS proof (`xcrun stapler validate`, `spctl -a -t open -vv`, Team `F9W689P9NE`) and add a `workflow_dispatch` attest job that re-verifies and attests published dmgs, so FR-012 holds for every artifact.

**Windows (FR-013)**: unsigned by ruling (spec 063:31); the text already exists in `packaging/release-notes.md:6`, `install.md:50`, `en.ts:715`, `ARCHITECTURE.md:116`. The new verification docs must say attestation does not remove the SmartScreen prompt. Also stale: `extension/release-notes.md:14` names a `SHA256SUMS-extension` nothing produces, and `get-started/+page.svelte:43` links a README anchor that no longer exists.

**iOS privacy manifest (FR-014)**: no `.xcprivacy` anywhere; three targets only (app, unit tests, UI tests), no extensions. Measured API usage: Swift uses `UserDefaults` only (`Core/VelaStore.swift:108`, `AccountStore.swift:27`) → category `UserDefaults`, reason `CA92.1`. The **binary** additionally imports `_stat/_fstat/_fstatat/_lstat` (FileTimestamp) and `_fstatfs` (DiskSpace) — traced to `rust/crates/vela-core-uniffi/Cargo.toml:27` enabling uniffi's `cli` feature on the library, which links `uniffi_bindgen` (10 657 symbols) into the shipped app. `mach_absolute_time` is **not** imported, so no SystemBootTime declaration is needed. Decision: split the `uniffi-bindgen` binary out of the shipped crate, re-measure, then declare only what survives. Lottie 4.6.1 ships its own manifest; `VelaCoreKit` is a **static** xcframework, so its symbols are the app's responsibility. The file can be committed at `app-ios/VelaWallet/VelaWallet/PrivacyInfo.xcprivacy` with **no pbxproj edit** (folder-synchronised group, objectVersion 77). Validate with Xcode's privacy report on an archive, plus a CI gate: `plutil -lint`, bundle-root presence, and an `nm -u` regression check against the declared categories.

## 5. Hygiene and the service repos (items 3, 11, 12, 13 → FR-003/15/16/17)

**Dormant site routes (FR-015)**: `api/{wallet,transactions,nft,bundler,proxy}` all read private env and call Alchemy or Pimlico; `proxy/+server.ts:33` is an open fetch-and-pipe with an SSRF blocklist (`:5-31`) that misses 169.254, decimal-IP and IPv6-mapped forms. **No caller exists**: a repo-wide grep over this repo, vela-relay and p256-index for `getvela.app/api` and each path finds only prose in `specs/` and `docs/`; spec 039 already recorded "no caller in the Worker wallet today" (`specs/039-retire-expo-tree/results.md:420`). Keep `og`, `downloads` (used by get-started, R2 binding, tested), `bug-report`, and `exchange-rate` (its only reference `wallet-api.ts:313` is itself dead, but it is the deployment smoke test — keep and flag). `hooks.server.ts:68` scopes CORS to `/api/*` generically, so deletion needs no hooks change; no tests cover the five. Stale takeover docs to correct with the deletion: `docs/project-takeover/{01,02,05,06,08,11}`.

**Feedback (FR-016)**: the web panel `FeedbackBody.svelte` takes an `onsend` prop (:16) that `SettingsHome.svelte:537` never passes — the button is inert; the row is also filtered out of the live phone settings (`settings/+page.svelte:436`) and absent from desktop, so today it is reachable only in `/gallery`. Preview lines are fiction (`fixtures.ts:806`) while the consent text promises the preview is what is sent. The site endpoint is complete and defensive: required `what`, 16 000-char cap → 413, per-IP 5/10 min → 429, **503 `not_configured`** when no token so clients can fall back, fingerprint dedup → comment, else creates a labelled issue (`api/bug-report/+server.ts:21-177`). Android opens a prefilled issue URL instead (`VelaNavHost.kt:1661`), iOS's send is literally `{}` (`SettingsSheet.swift:336`), desktop has none. **GitHub gotcha**: with `template=bug.yml`, `&body=` is ignored — prefill must use field ids (`&what=`, `&environment=`), so Android's current URLs silently lose the body. Decision: a shared `bug-report.ts` service in the web wallet POSTing to the endpoint with a prefilled-URL fallback on 503/429/5xx, real preview lines, and the row reachable; include app version/commit, platform, language, failed chain names and counters; exclude addresses, balances, endpoint/RPC URLs (they carry keys) and raw `vela.*` values.

**Erase (FR-017)**: the web module is the reference (`services/erase-device.ts`: prefix sweep over localStorage + IndexedDB `vela/kv` + `chrome.storage.local`, keep-list `['vela.pendingUploads']`, verify-or-throw), but even web's wide layout card has no `onselect` (`SettingsDesktop.svelte:212`). Desktop's `danger_card` (`settings/components.rs:895`) has no click handler at all; its state is one JSON doc (`executor/storage.rs:85`) plus a wry webview using the platform default data store (`webview.rs:326`), so it needs `clear_all_browsing_data()`. iOS keeps a hand-written delete list (`RootView.swift:2758`) missing ~14 key groups, never touches `WKWebsiteDataStore` (every dApp's cookies/localStorage/IndexedDB — `BrowserEngine.swift:78`) nor the logo `URLCache`, and calls `session.signOut()` which only *opens* the confirmation (`session.rs:359`). Android's `DeviceStorage.erase` (`DeviceStorage.kt:86`) misses WebView data, the `settings` DataStore, crash prefs, log files and caches. No core erase event exists; erase stays shell-owned (as web documents) with a shared contract in `contracts/`.

**Service repos (FR-003)**: p256-index `.env.example` is worse than audited — `P256_INDEX_CONTRACT_ADDRESS` is *commented out* while `config.rs:80` requires it (the server exits at boot), and `P256_INDEX_DOMAIN_REGISTRY` is absent while `config.rs:81` defaults it to the contract address, which is wrong after V13. Its `p256-index-server/Dockerfile:16` copies only two of three workspace members (`p256-replay` was added later), so the build fails resolving the workspace; `docker-compose.yaml:17` requires a gitignored `.env`. vela-relay's `Dockerfile:14` predates the core/cf split: it misses the `vela-relay-core` and `vela-relay-cf` members, `build.rs` + `build_info.rs` (the root build script `include!`s it) and `contracts/alto/*.json` (`include_str!` at `worker/executor/deployment.rs:20`). Both fixes are small and mechanical; once they land, the site's "may not build" caveats (`self-hosting.md:157,233` + 13 locales) must come out.

## Cross-cutting decisions

- **Verification per item** is defined in [quickstart.md](quickstart.md); native changes are additionally exercised on the connected Xiaomi (Android) and iPhone 11 per FR-019.
- **Shipping order** follows the dependency chain in [plan.md](plan.md): core rules and wire types first (they force regenerated bindings), then shells, then site/docs.
- **Parity scripts are too weak**: `scripts/check-ios-android-parity.mjs` and `check-android-event-parity.mjs` compare only the event `"type"` string, which is exactly how the iOS payload mismatch survived. Extending them to compare payload keys against the generated `NetEvent.ts` is the cheapest guard against the whole bug class, and belongs in this feature.
