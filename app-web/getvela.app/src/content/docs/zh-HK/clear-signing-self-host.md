# 自行架設簽名頁

Vela 會在你批准每一筆交易之前先解碼，這份解碼是認真的工作——但做這份工作的，正是建構這筆交易的同一個
App。如果這個 App 或它送到你手上的途徑被人動了手腳，它就可以給你看一樣東西，卻簽署另一樣東西。
[Bybit](/zh-HK/docs/bybit-attack) 遇到的正是這種情況。

簽名頁的存在，就是要把這件事一分為二：交易從一個地方來，而核對和簽署則在一個由你控制的地方進行。


一個資料夾——程式碼庫中的 `app-web/clearsigning`——它既是一個網頁，也是一個 Chrome 擴充功能。純 HTML、
CSS 和 JavaScript：沒有框架、沒有打包工具、沒有建置步驟、沒有依賴，也不會從伺服器取得任何資料——它唯一的
請求，是載入裝飾用的代幣標誌。

收到簽署請求時，它不會相信隨請求附上的摘要。它會自行解碼原始 calldata、自行計算雜湊值（digest），向你
顯示這個簽名實際會授權甚麼，然後才請求你的通行密鑰。

由於沒有建置步驟，你閱讀的檔案就是實際運行的檔案。你可以把這個資料夾與程式碼庫逐一比對，從而確切知道
自己提供的是甚麼。

## 哪一份副本能為你的錢包簽署

通行密鑰綁定在建立它的域名上。你的 Vela 鑰匙登記在 `getvela.app` 之下，瀏覽器只會把它們提供給依賴方
（relying party）是 `getvela.app` 的頁面。就是這一條規則，決定了哪一種自行運行副本的方式對你有用。

**作為你自己域名或 localhost 上的頁面。**以 HTTPS（或從 localhost）提供時，頁面的依賴方就是它自己的主機
名稱——所以它能用登記在*該*主機名稱下的鑰匙簽署，而不能用登記在 `getvela.app` 下的鑰匙。因此，這種方式
適合用來端對端試行整個簽署流程、運行桌面版流程，以及為鑰匙建立在你自己域名上的錢包簽署。它並不能為
現有的 `getvela.app` 錢包簽署。

```sh
cd app-web/trusted-signer
python3 -m http.server 8080   # → http://localhost:8080
```

App 中的所有路徑都是相對路徑，所以放在現有主機的子目錄下也可以運作；直接從磁碟打開 `index.html`
（`file://`）也能隨便看看——不過那樣沒有來源（origin），也就沒有依賴方，甚麼都簽署不了。

## 簽署前它會做甚麼

- **它自行解碼交易。**這個呼叫做甚麼、給誰、多少，全部從 calldata 讀出——包括嵌套在批量交易中的呼叫。
- **它只簽署自己計算出的雜湊值。**EIP-191、EIP-712、SafeOp 和 SafeMessage 的雜湊值都在頁面中計算，並與
  錢包使用的同一份程式碼 `vela-core` 交叉核對。無法計算的雜湊值會被拒絕，而不是照樣簽署。
- **它會檢查交易正是被請求的那一筆。**網站請求的呼叫，必須真的包含在被簽署的操作之中。
- **它會指出「無限」授權。**它無法更改金額——它只會簽署收到的那些位元組，否則甚麼都不簽——所以無限的授權或
  permit（在本頁為 2^128 或以上）會以紅色顯示並註明這個原因，而且可以按原樣簽署；鏈上授權的上限，要在請求
  到達這裏之前，在錢包自己的授權畫面上選定。針對整個 NFT 系列的授權會被拒絕。
- **它讀不懂時會直說，**而不是顯示一段它無法負責的友善摘要。
- **它會顯示帳戶的地址和識別圖案（identicon），**但不會顯示由請求簽署的一方提供的收款方名稱。凡是請求方
  能控制的內容，要麼被丟棄，要麼被標示為來自請求方。

## 它刻意沒有的功能

- **沒有編輯功能。**請求一到達就已固定：你要麼簽署，要麼不簽。手續費選擇器或額度編輯器都會改寫 calldata，
  而這正是這個頁面要防止的毛病。
- **不能建立鑰匙。**簽名頁無法建立通行密鑰。建立一把新鑰匙，就等於建立一個不同的帳戶。
- **不從網絡取得資料。**它顯示或簽署的內容，沒有一樣是從網絡取得的。它唯一載入的是代幣標誌，以圖片形式
  從 Vela 的鏈數據伺服器取得；如果載入失敗，會以一個字母代替。

## 請求如何到達它

| 請求方                                       | 傳遞途徑                                                                   |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| 同一瀏覽器中的頁面                           | `postMessage`                                                              |
| 同一瀏覽器中的頁面，傳給擴充功能             | 擴充功能連接埠（port）                                                     |
| 同一部電腦上的桌面 App                       | URL 片段 + 本機回環（loopback）回呼（`samples/` 中有示範；Vela 桌面版目前尚未使用） |
| 手機或另一部電腦                             | 藍牙低功耗（協議已實作；無線電部分尚未在實體硬件上測試）                   |

傳輸格式、雜湊值的計算方式，以及一張說明畫面上每一項內容來源的對照表，都在程式碼旁邊的 `PROTOCOL.md` 中。

## 它的定位

當各個 App 能把請求交給它之後，預期的用法很簡單：從帳戶存有你不想損失的錢那天起，每一次簽署都經過一個由
你親自載入程式碼的頁面。不只是大額交易——一筆小小的授權，就可能交出足以掏空帳戶的權限。在此之前，這個
頁面讓你可以閱讀和測試那個「第二意見」將會如何運作。
