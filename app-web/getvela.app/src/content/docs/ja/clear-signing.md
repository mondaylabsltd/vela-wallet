# クリア署名

多くのウォレットは、知らないコントラクトについてはいまも生のデータをそのまま表示します。そして「ブラインド署名」、つまり実際には読めない呼び出しを承認することは、ウォレットから資金を抜かれる経路のひとつです。Vela の答えが**クリア署名**です。署名の前に、取引をできるかぎり、あなたが理解できる形にデコードします。

## 何が表示されるか

生の calldata の代わりに、Vela は次のものを表示します。

- **意図** —— その取引が何をするのか。*送る*、*承認*、*交換* など。
- **中身** —— 関わる金額とアドレス。トークンの額は実際の単位で表示し、名前がわかる受取人は名前で表示します。
- **詳細** —— nonce、期限、生の calldata。いきなり目の前に突きつけるのではなく、必要なときに開けるようにしています。
- **リスクの目安** —— 危険な操作が目立つように色分けします。

## しくみ（ERC-7730）

Vela は [ERC-7730](https://github.com/LedgerHQ/clear-signing-erc7730-registry) のディスクリプターを使って、**コントラクトの呼び出し**と **EIP-712 の型付きデータ**の両方をデコードします。ディスクリプターとは、あるコントラクトの関数が何を意味するのかを記した、小さく共有できる定義です。

Vela は次の順でディスクリプターを探します。

1. **アプリに内蔵** —— 広く使われているコントラクトのディスクリプター。Uniswap、PancakeSwap、SushiSwap のルーター、WETH、Aave v3 のプール、1inch、Lido と wstETH、Seaport です。
2. **Vela のチェーンデータサーバーから取得** —— 公開の ERC-7730 レジストリを再配信しているものです。
3. **標準の形** —— ERC-20 トークン、ERC-721 と ERC-1155 の NFT、ERC-4626 のボールト、ERC-2612 の permit。これで、日常の操作のほとんどはデコードできます。

**検証済み**は、最初の出どころだけに使う言葉です。取引が検証済みと表示されるのは、その説明が、いま動かしているアプリに組み込まれたディスクリプターから来たときか、チェーンデータサーバーから来たうえで組み込みのものと完全に一致するとき（途中で何も書き換えられていない証拠になります）だけです。サーバーが返すそれ以外のものも、これまでどおりデコードして表示しますが、ディスクリプターサービスから来たもので、それを認証したものは何もない、という一行が添えられます。そのサービスには署名がないので、信頼性は運用している人の信頼性と同じです。これも、[自分で動かせる](/ja/docs/self-hosting#chain-data)ようにしている理由のひとつです。

トークンの額は、そのトークンの**オンチェーンの実際の小数点以下の桁数**で整形します。桁数を確認できない場合は、18 桁と仮定して額を表示し、**未検証と明示します**。間違っているかもしれない数字が、確認済みの数字のように見えることはありません。

## リスクレベル

デコードされた取引にはすべてリスクレベルが付き、危険なパターンが目立つようになっています。

- **注意** —— 承認や permit。資金を使う権限を渡す操作です。
- **危険** —— 本当に危ないもの。たとえば**無制限のトークン承認**。
- ステーキングや預け入れのような日常的な操作は、それより低いリスクです。

<Callout type="warning" title="「無制限」のオンチェーン承認は送信できません">
無制限の額のオンチェーン承認は、あとで資金を抜かれる最もよくある経路のひとつです。dApp が「無制限」レベルの承認（<code>approve</code>、<code>increaseAllowance</code>、Permit2 の <code>approve</code>）を求めてきたとき、つまり dApp が「無制限」の意味で使う 2^200 以上（Permit2 では 2^152 以上）の額の場合、具体的な額、あなたの残高、または取り消しに変更するまで、Vela はそれを送信しません。送信前の最終チェックは生の calldata を読むので、ディスクリプターの有無にかかわらず働きます。止められないものもあります。<strong>大きいが有限の額の承認</strong>（残高をはるかに上回る額でも）、<strong>署名による許可</strong>（EIP-2612 や Permit2 の署名）、そして NFT の <code>setApprovalForAll</code> です。これらはいずれも注意を表示したうえで、判断をあなたに委ねます。
</Callout>

## Vela がデコードできないとき

ERC-7730 のディスクリプターはないものの、その関数が公開のセレクターデータベースに載っている場合、Vela は汎用的にデコードし、注意のバナーの下に**ベストエフォート**（デコードはできたが検証はされていない）と表示します。それもできない場合や、取引の一部しかデコードできない場合、Vela は理解したふりを**しません**。

<Callout type="danger" title="ブラインド署名の明確な警告">
呼び出しをデコードできないとき、Vela はもっともらしい偽の要約ではなく、はっきりしたブラインド署名の警告を表示します。一部のフィールドしか読み取れないときは、表示が部分的であることを伝え、リスクレベルを高いままにします。署名しようとしているもののうち、Vela が実際に読めたのがどこまでなのか、あなたは常に把握できます。
</Callout>

## これが重要な理由

セルフカストディとは、まずい取引を誰も代わりに取り消してくれないということです。身を守る手段はサポート窓口ではなく、承認する**前に**、何を承認するのかを理解することです。クリア署名は、それを示そうとする Vela の取り組みですが、限界もあります。表示しているアプリ以上に正直にはなれません。だからこそ[独立した確認](/ja/docs/clear-signing-self-host)が重要になります。Vela のセキュリティモデルにおける位置づけは[ホワイトペーパー](/ja/docs/whitepaper)を参照してください。
