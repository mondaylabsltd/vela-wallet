# 署名ページを自分で動かす

Vela は承認の前にすべての取引をデコードしますし、そのデコードは誠実な仕事です。けれど、その仕事をしているのは、取引を組み立てたのと同じアプリです。アプリ自体、あるいはアプリがあなたに届く経路が改ざんされれば、あるものを見せて、別のものに署名させることができます。[Bybit](/ja/docs/bybit-attack) で起きたのは、まさにそれでした。

署名ページは、それを 2 つに分けるために存在します。取引はある場所から届き、確認と署名は、あなたが管理する別の場所で行われます。


リポジトリの `app-web/clearsigning` というひとつのフォルダーで、ウェブページでもあり、Chrome 拡張でもあります。素の HTML、CSS、JavaScript だけでできていて、フレームワークも、バンドラーも、ビルド手順も、依存関係もなく、サーバーからデータを取得することもありません。唯一の通信は、飾りとしてのトークンのロゴの取得です。

署名リクエストを受け取っても、一緒に送られてきた要約は信じません。生の calldata を自分でデコードし、ダイジェストを自分で計算し、その署名が実際に何を認可するのかを示したうえで、はじめてパスキーに署名を求めます。

ビルド手順がないので、読んだファイルがそのまま動くファイルです。フォルダーをリポジトリと差分比較すれば、自分が配信しているものが何なのかがわかります。

## どのコピーがあなたのウォレットのために署名できるか

パスキーは、作成されたドメインに結び付いています。あなたの Vela の鍵は `getvela.app` の下に登録されていて、ブラウザは、リライングパーティー（relying party）が `getvela.app` であるページにしかそれを提示しません。自分のコピーを動かす方法のうち、どれが役に立つかは、この 1 つのルールで決まります。

**自分のドメインや localhost 上のページとして。**HTTPS で（または localhost から）配信すると、ページのリライングパーティーはそのホスト名になります。つまり、*そのホスト名*の下に登録された鍵では署名できますが、`getvela.app` の下に登録された鍵では署名できません。一連の手順を端から端まで試すのに、デスクトップのフローを動かすのに、そして自分のドメインで鍵を作ったウォレットのために署名するのに向いた方法です。既存の `getvela.app` のウォレットのために署名する方法ではありません。

```sh
cd app-web/trusted-signer
python3 -m http.server 8080   # → http://localhost:8080
```

アプリ内のパスはすべて相対パスなので、既存のホストのサブディレクトリに置いても動きます。`index.html` をディスクから直接（`file://` で）開いても、中を眺めることはできます。ただしオリジンがないので、リライングパーティーもなく、何にも署名できません。

## 署名の前にすること

- **取引を自分でデコードします。**その呼び出しが何をするのか、誰に、いくらなのかを、calldata から読み取ります。バッチの中に入れ子になった呼び出しも含みます。
- **自分で計算したダイジェストにしか署名しません。**EIP-191、EIP-712、SafeOp、SafeMessage のダイジェストをページ内で計算し、ウォレットと同じコードである `vela-core` と照合します。計算できないダイジェストは、署名ではなく拒否になります。
- **求められた取引と同じものかを確認します。**サイトが求めた呼び出しが、署名される操作の中に実際に含まれていなければなりません。
- **「無制限」レベルの承認を拒否します。**警告ではなく拒否で、代わりにどうすればいいかも示します。
- **読めないものは、読めないと言います。**責任を持てない、もっともらしい要約を表示することはありません。
- **アカウントのアドレスとアイデンティコンを表示し、**署名を求めた側が渡してきた受取人の名前は表示しません。リクエストを送った側が操作できるものは、捨てるか、相手が示したものだと明記します。

## あえて持たないもの

- **編集機能はありません。**リクエストは届いた時点で確定しています。署名するか、しないかだけです。手数料の選択や上限額の編集は calldata を書き換えることになり、それこそこのページが防ごうとしている病です。
- **鍵を作成できません。**署名ページはパスキーを作れません。鍵を作ることは、別のアカウントを作ることだからです。
- **ネットワークからデータを取得しません。**表示するものも、署名するものも、どれも取得したものではありません。読み込むのはトークンのロゴだけで、Vela のチェーンデータサーバーから画像として読み込みます。読み込めなければ、代わりに文字を表示します。

## リクエストの届き方

| リクエスト元                                 | 経路                                                                       |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| 同じブラウザのページ                         | `postMessage`                                                              |
| 同じブラウザのページから拡張機能へ           | 拡張機能のポート                                                           |
| 同じマシンのデスクトップアプリ               | URL フラグメント + ループバックコールバック（`samples/` にデモあり。Vela のデスクトップアプリはまだ使っていない） |
| スマートフォンや別のコンピューター           | Bluetooth LE（プロトコルは実装済み。無線部分は実機で未検証）               |

通信形式、ダイジェスト、そして画面上の各項目がどこから来ているかの対応表は、コードの隣にある `PROTOCOL.md` にあります。

## 位置づけ

アプリがリクエストをこのページに渡せるようになれば、想定している使い方はシンプルです。失ったら困る額のお金がアカウントに入った日から、すべての署名を、自分で読み込んだコードのページに通すことです。大きな額のときだけではありません。小さな承認ひとつで、アカウントを空にできるほどの権限を渡してしまうこともあります。それまでのあいだ、このページは、そのセカンドオピニオンがどう働くのかを、実際に読んで試すためのものです。
