# 自己架設簽署頁

Vela 在你核准每一筆交易之前都會先解碼，而這份解碼是實實在在的工作——但做這件事的，是
組出這筆交易的同一個應用程式。如果這個應用程式、或它送到你手上的那條路被動了手腳，
它就能給你看一樣東西、卻簽下另一樣。[Bybit](/zh-TW/docs/bybit-attack) 遇到的正是這件事。

簽署頁存在的意義，就是把這件事一分為二：交易從一個地方來，而核對和簽署發生在
另一個由你控制的地方。

**狀態：** 已完成並在本機測試過；**尚未發布**，而且**目前還沒有任何 Vela 應用程式會把請求送給它**。
現階段它可以拿來閱讀、執行，並用 `samples/` 資料夾裡的示範請求端試用。要真正用它來簽署，
還需要各個應用程式把請求轉給它，這部分還沒開發。

## 它是什麼

一個資料夾——儲存庫裡的 `app-web/clearsigning`——它既是一個網頁，也是一個 Chrome 擴充功能。
純 HTML、CSS 和 JavaScript：沒有框架、沒有打包工具、沒有建置步驟、沒有相依套件，
也不會從伺服器取得任何資料——唯一的請求是裝飾用的代幣圖示。

收到一個簽署請求時，它不相信隨請求一起送來的摘要。它會自己解碼原始 calldata、
自己算出摘要值、把這個簽章實際會授權的內容攤開給你看，然後才去請求你的密碼金鑰。

因為沒有建置步驟，你讀到的檔案就是實際在執行的檔案。你可以把這個資料夾和儲存庫逐一比對，
確切知道自己架設的是什麼。

## 哪一份副本才能替你的錢包簽署

密碼金鑰綁定在它建立時的那個網域上。你的 Vela 金鑰是註冊在 `getvela.app` 底下的，
而瀏覽器只會把它們提供給依賴方（relying party）是 `getvela.app` 的頁面。
這一條規則，決定了哪一種「自己跑一份」的方式對你有用。

**當作 Chrome 擴充功能——要用你現有的金鑰，就用這個方式。** 不管這個資料夾從哪裡來，
擴充功能的依賴方都是 `getvela.app`，所以你現有的金鑰可以在裡面簽署，而執行的程式碼
正是你載入並檢查過的那個資料夾。

1. 取得資料夾：`git clone https://github.com/mondaylabsltd/vela-wallet`（就是裡面的
   `app-web/clearsigning`）。
2. 開啟 `chrome://extensions`，啟用「開發人員模式」。
3. 點「載入未封裝項目」，選擇 `app-web/clearsigning` 資料夾。
4. 工具列上的圖示會在分頁裡打開這個頁面。

**當作你自己網域上、或 localhost 上的網頁。** 透過 HTTPS（或在 localhost 上）提供服務時，
這個頁面的依賴方就是它自己的主機名稱——所以它能用註冊在*那個*主機名稱底下的金鑰簽署，
而不是註冊在 `getvela.app` 底下的金鑰。這讓它很適合拿來把整套流程從頭到尾跑一遍、
執行桌面端的流程，以及替金鑰是在你自己網域上建立的錢包簽署。它不是用來
替已經存在的 `getvela.app` 錢包簽署的方法。

```sh
cd app-web/clearsigning
python3 -m http.server 8080   # → http://localhost:8080
```

應用程式裡所有路徑都是相對路徑，所以放在現有主機的子目錄底下也能用；直接從磁碟打開
`index.html`（`file://`）也可以隨意看看——那種情況下沒有來源，也就沒有依賴方，
什麼都簽不了。

## 它在簽署之前會做什麼

- **它自己解碼交易。** 這個呼叫在做什麼、給誰、多少錢，全都從 calldata 讀出來
  ——包括批次交易裡巢狀的呼叫。
- **它只簽自己算出來的摘要值。** EIP-191、EIP-712、SafeOp 和 SafeMessage 的摘要值都在
  頁面裡計算，並和 `vela-core`——錢包用的同一份程式碼——交叉比對。算不出來的摘要值就是拒絕簽署，
  而不是照簽。
- **它會檢查這筆交易就是被請求的那一筆。** 網站請求的那個呼叫，必須真的在被簽署的
  操作裡面。
- **它拒絕「無上限」的授權。** 不是警告——是拒絕，並告訴你該改成怎麼做。
- **它讀不懂的時候會直說，** 而不是拿一段自己也不敢保證的友善摘要來充數。
- **它會顯示帳戶的位址和識別圖示，** 而且不顯示由要求簽章的一方提供的收款人名字。凡是請求端
  能控制的東西，不是被拿掉，就是被明確標示成「這是對方提供的」。

## 它刻意不具備的功能

- **沒有任何編輯器。** 請求一送到就固定了：你要嘛簽，要嘛不簽。手續費選擇器或額度
  編輯器都會改寫 calldata，而那正是這個頁面要防的毛病。
- **不能建立金鑰。** 簽署頁無法建立密碼金鑰。建立一把新金鑰，就等於建立一個
  不同的帳戶。
- **不從網路取得資料。** 它顯示和簽署的內容，沒有一樣是從網路取得的。它唯一會載入的是代幣圖示，以圖片形式
  從 Vela 的鏈資料伺服器取得；載入失敗時會用一個字母代替。

## 請求怎麼送到它這裡

| 請求端                                        | 通道                                                                       |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| 同一個瀏覽器裡的網頁                          | `postMessage`                                                              |
| 同一個瀏覽器裡的網頁，送給擴充功能            | 擴充功能連接埠（port）                                                     |
| 同一台電腦上的桌面應用程式                    | URL 片段 + 回送位址（loopback）回呼（`samples/` 裡有示範；Vela 桌面版目前還沒採用） |
| 一支手機或另一台電腦                          | 藍牙低功耗（BLE）（協定已實作；無線電部分還沒在實機上測試過）             |

傳輸格式、摘要值演算法，以及一張「畫面上每一項資訊從哪裡來」的對照表，都在程式碼旁邊的
`PROTOCOL.md` 裡。

## 它的定位

等各個應用程式能把請求交給它之後，用法很簡單：從帳戶裡放著你輸不起的錢那天起，每一次簽署都
經過一個由你親手載入程式碼的頁面。不只是大額的時候——一筆很小的授權，就可能交出足以把帳戶
掏空的權限。在那之前，這個頁面讓你能先讀、先試那份「第二意見」將會怎麼運作。
