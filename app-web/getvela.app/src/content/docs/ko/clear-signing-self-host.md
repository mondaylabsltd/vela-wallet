# 서명 페이지 직접 호스팅

Vela는 승인하기 전에 모든 거래를 디코딩하고, 그 디코딩은 성실하게 이루어집니다. 하지만 그
작업을 하는 것은 거래를 만든 바로 그 앱입니다. 앱이나 앱이 사용자에게 전달되는 경로가
변조되면, 한 가지를 보여 주고 다른 것에 서명하게 할 수 있습니다.
[바이비트](/ko/docs/bybit-attack)에서 일어난 일이 정확히 그것입니다.

서명 페이지는 이것을 둘로 나누기 위해 있습니다. 거래는 한 곳에서 오고, 확인과 서명은 사용자가
통제하는 다른 곳에서 이루어집니다.


저장소의 `app-web/clearsigning` 폴더 하나이며, 웹 페이지이자 Chrome 확장 프로그램입니다.
순수한 HTML, CSS, JavaScript로만 되어 있습니다. 프레임워크도, 번들러도, 빌드 단계도,
의존성도 없고, 서버에서 데이터를 가져오지도 않습니다. 유일한 요청은 장식용 토큰 로고입니다.

서명 요청을 받으면 함께 온 요약을 믿지 않습니다. 원시 calldata를 스스로 디코딩하고, 다이제스트를
직접 계산하고, 그 서명이 실제로 무엇을 허락하는지 보여 준 다음에야 패스키에 서명을
요청합니다.

빌드 단계가 없으므로 읽은 파일이 곧 실행되는 파일입니다. 폴더를 저장소와 비교(diff)해 보면
무엇을 서비스하고 있는지 정확히 알 수 있습니다.

## 어떤 사본이 내 지갑에 서명할 수 있나

패스키는 만들어질 때의 도메인에 묶입니다. Vela의 키는 `getvela.app` 아래에 등록되어 있고,
브라우저는 신뢰 당사자(relying party)가 `getvela.app`인 페이지에만 이 키를 내어 줍니다. 이
규칙 하나가, 사본을 직접 운영하는 여러 방법 중 무엇이 쓸모 있는지를 결정합니다.

**내 도메인이나 localhost의 페이지로 쓰기.** HTTPS로(또는 localhost에서) 서비스하면 페이지의
신뢰 당사자는 그 페이지 자신의 호스트 이름이 됩니다. 따라서 `getvela.app` 아래에 등록된 키가
아니라 _그_ 호스트 이름 아래에 등록된 키로 서명할 수 있습니다. 전체 과정을 처음부터 끝까지
시험해 보거나, 데스크톱 흐름을 실행하거나, 키를 내 도메인에서 만든 지갑에 서명할 때 알맞은
방법입니다. 기존 `getvela.app` 지갑에 서명하는 방법은 아닙니다.

```sh
cd app-web/trusted-signer
python3 -m http.server 8080   # → http://localhost:8080
```

앱의 모든 경로는 상대 경로이므로 기존 호스트의 하위 디렉터리에 두어도 작동합니다. 디스크에서
`index.html`을 바로 열어도(`file://`) 둘러보는 데는 문제가 없지만, 출처(origin)가 없으니 신뢰
당사자도 없고 아무것도 서명할 수 없습니다.

## 서명하기 전에 하는 일

- **거래를 스스로 디코딩합니다.** 호출이 무엇을, 누구에게, 얼마나 하는지 calldata에서
  읽어 냅니다. 묶음 안에 들어 있는 호출도 포함합니다.
- **직접 계산한 다이제스트에만 서명합니다.** EIP-191, EIP-712, SafeOp, SafeMessage 다이제스트를
  페이지 안에서 계산하고, 지갑이 쓰는 것과 같은 코드인 `vela-core`와 교차 검증합니다.
  계산할 수 없는 다이제스트는 서명하지 않고 거부합니다.
- **요청받은 거래가 맞는지 확인합니다.** 사이트가 요청한 호출이 서명할 오퍼레이션 안에 실제로
  들어 있어야 합니다.
- **"무제한" 수준의 승인은 거부합니다.** 경고가 아니라 거부이며, 대신 무엇을 하면 되는지
  알려 줍니다.
- **읽지 못하는 것이 있으면 그렇다고 말합니다.** 책임질 수 없는 친절한 요약을 대신 보여 주지
  않습니다.
- **계정 주소와 아이덴티콘을 보여 주고**, 서명을 요청한 쪽이 넘겨준 받는 사람 이름은 보여 주지
  않습니다. 요청하는 쪽이 제어할 수 있는 것은 빼거나, 요청한 쪽이 제공한 것이라고 표시합니다.

## 일부러 넣지 않은 것

- **편집 기능이 없습니다.** 요청은 도착한 순간 고정됩니다. 서명하거나, 하지 않거나 둘 중
  하나입니다. 수수료 선택이나 한도 편집 기능은 calldata를 다시 쓰게 되는데, 그것이야말로 이
  페이지가 막으려는 병입니다.
- **키를 만들지 않습니다.** 서명 페이지는 패스키를 만들 수 없습니다. 키를 새로 만드는 것은 다른
  계정을 만드는 것이기 때문입니다.
- **네트워크에서 데이터를 가져오지 않습니다.** 보여 주거나 서명하는 내용 중 가져온 것은 없습니다.
  불러오는 것은 Vela 체인 데이터 서버의 토큰 로고 이미지뿐이고, 불러오지 못하면 글자 하나가
  대신 표시됩니다.

## 요청이 전달되는 방법

| 요청하는 쪽                                  | 채널                                                                       |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| 같은 브라우저의 페이지                       | `postMessage`                                                              |
| 같은 브라우저의 페이지에서 확장 프로그램으로 | 확장 프로그램 포트                                                         |
| 같은 컴퓨터의 데스크톱 앱                    | URL 프래그먼트 + 루프백 콜백(`samples/`에 데모 있음. Vela 데스크톱 앱은 아직 사용하지 않음) |
| 휴대폰이나 다른 컴퓨터                       | 블루투스 LE(프로토콜은 구현, 무선 부분은 실제 기기에서 아직 테스트하지 않음) |

전송 형식, 다이제스트, 그리고 화면의 각 항목이 어디서 오는지 정리한 표는 코드 옆의
`PROTOCOL.md`에 있습니다.

## 어디에 쓰나

앱이 요청을 이 페이지로 넘길 수 있게 되면 쓰는 방법은 간단합니다. 잃으면 곤란한 금액이
계정에 들어간 날부터, 모든 서명을 직접 로드한 코드로 돌아가는 페이지에서 하는 것입니다. 큰
금액일 때만이 아닙니다. 작은 승인 하나로도 계정을 비우기에 충분한 권한을 넘겨줄 수 있습니다.
그때까지 이 페이지는 그 두 번째 의견이 정확히 어떻게 작동할지 읽고 시험해 보는 수단입니다.
