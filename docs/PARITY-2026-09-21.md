## 3. 需要人来决定

### D1 · #273 Explore 扫码按钮（四端）
事实：Android 的扫码图标只是"提交输入框文字"；web 和 iOS 画了按钮但没接事件；**四端都不支持 WalletConnect**（核心里唯一的远程配对是自研的 WalletPair，桌面已于 2026-09-08 裁定不接，手机也没接）。所以"扫 WalletConnect 码连 dApp"这一期望，改按钮本身满足不了。

选项：
- (a) 四端**先移除** Explore 的扫码图标。
- (b) **改成通用扫码**：URL → 内置浏览器打开；`ethereum:`/地址 → 发送（首页扫码路径已存在：核心 `scan_resolved`）；`wc:` → 如实提示"暂不支持 WalletConnect，请在 Explore 浏览器里打开该 dApp"。
- (c) **实现 WalletConnect v2**：新产品面 + 新依赖 + 安全评审。

建议 (b)：改动小、诚实、复用现有机器，同时引导用户走内置浏览器。

### D2 · #262 钱包以外的三个后续
PR #279 已阻止"用不持有的币付费"。以下三点各需一个负责人裁定：
1. **bundler 永久保留无法报销的 op**：`vela-bundler` `shared/bundler/index.ts` 约 1396–1519（代码阅读所得）在打包时做 2× 报销检查，失败返回 `submitted:false` 但不 `dropWithReceipt`，钱包于是永远"等待确认"。建议 N 轮失败后带回执丢弃。
2. **费用在"实测 gas 下限"之前计价**：`fee_policy` 用中继原始 `callGasLimit` 求和（`fee_policy.rs` 约 2163）；spec 062 的内部调用下限只在提交时抬高 `callGasLimit`，显示/签名的费用不随之增长。对**未部署** Safe 的首笔合约调用（以太坊上的公钥备份正是如此）可能低估费用，同样会卡在打包检查。建议加一个 `FeeOperation` 让壳提供逐调用 `eth_estimateGas`，在计价前应用下限（核心 + 四端 fee executor）。
3. **回执等待超时被记为"已确认"**：120 秒后 `SignExecutor` 用 op hash 作答，`sign_request.rs` 约 1976–1992 把任何 `Succeeded(result)` 变成 `UpdateRecord Confirmed { tx_hash: result }`——记录显示"已确认"且 tx hash 其实是 op hash。建议保持 pending 交给 tracker（核心改动；web 路径可能依赖它，需一起看）。

### D3 · 对齐中的是/否问题
- **手续费速度与刷新（spec 068）上原生端**：web 是规格，但 web 把档位预览和"免费提速"逻辑写在 web TS 里而不在核心。直接移植 = 三个壳各复制一份钱规则。建议先把这部分规则搬进核心，再三端接线。要不要排期？
- **桌面：删除交易记录**：2026-09-09"两端都没有"的裁定已过时——web 现在能在交易详情里删除（`DeleteRequested`）。桌面要跟吗？
- **Android：首次向该地址转账提示（防投毒）**：web 回答 `first_time`，Android 恒为 `null`（`SendExecutor.kt` 约 171，原注明延后到 "T048"）。需要按对手方的历史索引，优先级？
- **iOS：10 分钟余额轮询**：web 有；iOS 没有与首页生命周期绑定的余额计时器，需新增生命周期接线。要不要？
- **iOS 分账时的"同资产手续费"警告**：web 在分账时只显示超额提示；iOS 保留了核心的同资产手续费警告（核心按分账总额计算）。保留还是与 web 一致去掉？
- **Android 设置页的 RPC 横幅**：web 没有，Android 的也从不绘制（ST1 fixture 无横幅）。是否从 live 路径删除？
- **"Use X for the empty rows"（分账一键填充空行）**：web 有，三个原生端都没有（需要新的事件路径）。要不要补？
- **桌面分账行没有地址输入框**：空行只能靠联系人或导入填地址；web 每行可输入。要不要补？
